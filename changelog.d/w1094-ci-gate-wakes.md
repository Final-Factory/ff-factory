- **A CI gate's end reaches the worker that set it** (w1094). When a `ci:` gate clears, FF Factory resumes the worker that set it with `blocked_on`, not the request's newest worker (w1049, PR #1507). If that worker is gone, the newest one is told the merge is its own now. While its CI runs, the setter keeps its request instead of being stopped as "with another worker now". A gate a worker sets cancels only its own check-in. A check-in the block held is handed back whenever the block ends, and folded into the resume instead of being overwritten. `blocked_on` takes any open request the worker holds (w1078 after w1095). A CI run hung for 6 hours wakes its worker instead of stalling the request. The ledger shows what the checks last said (`last read: …`), and a resumed worker waiting for a sandbox shows "waits for a sandbox on its machine". A sweep resumes again, loudly, a worker that has not taken its resume 5 minutes later (`ledger: SWEEP:`), and tells the dispatcher after 3 tries. One request that throws no longer ends the blocker watch's look for the others. The first look after a restart no longer crashes on `Cannot access 'usage' before initialization`. docs/orchestrators.md, "How the portal learns that CI finished", covers it, with the case for keeping polling over a webhook.
