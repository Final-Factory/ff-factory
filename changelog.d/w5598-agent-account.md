- **The portal's agents can run as their own OS account** (w5598, w5841): the orchestrators, the dispatcher and the bug-thread judge can start as `fff-agent` through `fff-agent.socket` (`deploy/vm/guest/fff-agent-launch`, `fff-agent@.service`), which can open no `/proc` of the portal's account, so neither the portal's memory nor its git and gh's `GH_TOKEN` are open to them; they see the portal's folders through idmapped views (`fff-agent-views`), so their transcripts and memory stay the portal's files, with a Claude login left in the portal's home and the push key (`vapid.json`) hidden, each instance in its own pid namespace, and an instance ending once the portal's side of its socket hangs up. It ships in `"warn"`, the default while config `agentAccount` is unset: every agent still starts as the portal's account, and a background check of the socket alerts the owners when it fails. `"on"` (set_app_config, or `fffctl agents on` on the VM) starts them as `fff-agent`: any failure before the launcher's OK starts that agent as before and alerts the owners, and two failed agents in 30 minutes switch them all back; `"off"`, or the ops worker's `fffctl agents off`, switches back at once. `fffctl fence-check` probes as `fff-agent` too, outside the unit (a stand-in git child) and inside it ([docs/vault.md](../docs/vault.md)). Needs a portal deploy.
