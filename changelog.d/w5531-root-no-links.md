- **Root follows no symbolic link into fff's folders** (w5531, finding 23 of the w5452 audit; lothsahn: "refuse symlinks before root's install -d"). fff owns `/srv/fff/data`, `config`, `home` and its other folders and can put a link in place of any of them, or of anything in them, at any moment; root's deploy steps wrote, chowned and chmodded there by name, so a link could have given fff a root-only folder or file, or had root overwrite one. Now (lib.sh, "root in fff's folders"): `tell_dispatcher`, `data_write`, `sync_public_url`, fff-update's `restore_inline_hash` and the guest install's config.json write are done by fff itself (a link leads fff only where fff could go anyway); `fff_dir` replaces root's `install -d -o fff` for fff's folders (install.sh's `/srv/fff/*`, `home/.ssh`, `home/.config/ffbox`, the dispatcher inbox), giving a root-made folder to fff with `chown -h` from inside its checked parent; any link at or above the path is refused and logged (`WARNING: ... refused: ... is a symbolic link`). fff-update gives a new release to fff bottom-up with `chown -h` and no longer chowns the reused `node_modules` copy while fff could write the release. fff-ops-priv's `apikey issue` reads the issued key as fff, from a folder of fff's inside root's own, and refuses a grant that is a link. `deploy/vm/test/fff-root-links.test.sh` (lint.sh --units, root) proves a link is refused, its target untouched, and a normal folder works.
